“WE’RE BUILDING A FHIR INTEGRATION” — WHICH ONE?

Does a person log in?

NO · SYSTEM TO SYSTEM

SMART Backend Services

  1. Your service signs a JWT with its key
  2. Auth server returns an access token
  3. Service calls FHIR — no human involved

Pipelines, feature jobs, Bulk $export

YES · USER FACING

SMART App Launch

  1. User opens the app from the EHR
  2. OAuth 2.0 login and consent
  3. App gets a token and patient context

Clinician apps, patient apps

Now the distinction that confuses more teams than any other. Someone says “we’re building a FHIR integration.” That sentence is incomplete, because there are two very different ways to authorize access to FHIR — and you need to know which one before you design anything. The question is simple: does a person log in? If no — it’s system to system — you use SMART Backend Services. Your service signs a JSON Web Token with its private key, the authorization server returns an access token, and your service calls the FHIR API. No human is involved. That’s how your pipelines, your feature jobs and your bulk exports work. You’ll implement exactly this with JWT client assertion in Track C. If yes — a person logs in — you use SMART App Launch. A clinician opens your app from inside the EHR, or a patient opens it on their phone. They log in with OAuth 2.0, and your app receives a token plus the context: which user, and which patient. Then it calls FHIR on that user’s behalf, limited to what they’re allowed to see. Same FHIR API underneath. Completely different security model, registration process and testing. Answer this question early. Teams that find out halfway through a build lose weeks re-doing their auth.
