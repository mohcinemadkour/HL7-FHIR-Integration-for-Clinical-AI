Section five: what happens when it fails. Because it will. Plan for three kinds of errors. Validation errors: the message itself is wrong — say OBX-5, the value, is empty. Reject it to an error queue, and an interface analyst reviews the queue every day. Business-rule errors: the message is valid, but it breaks a rule — the MRN doesn’t match any patient yet, maybe because the admission hasn’t arrived. Hold it, retry, and if it still fails, send it for review. System errors: the other side is down — the FHIR server times out. Retry with backoff, and page on-call if it keeps failing. For each type, the IDD answers three questions: what happens to the message, who gets alerted, and how it gets resolved. And log everything, successes and failures, for audit. Now the failure that’s specific to AI, in orange. The feed stops quietly. No errors — just no new messages. The model keeps running and keeps producing scores, on data that’s hours old. Nobody notices. So monitor freshness: alert when you haven’t received a message in longer than normal. That one alert has saved more pipelines than any error handler.
